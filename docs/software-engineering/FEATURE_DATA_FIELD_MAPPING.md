# Feature-to-Data Field Mapping

This map ties a proposed user journey to actual local SQLite fields and measured coverage. Counts refer to archive `full_archive_parquet_v1_20261028` and one retained source job-ad record unless noted. A field's presence does not prove correctness, currentness, completeness, or an employer requirement. Full row-wise coverage is in `analysis/reports/pre_backend/field_coverage.csv`; data definitions are in `docs/data/DATA_DICTIONARY.md`.

## Join and denominator rules

- `jobs.record_id` identifies a retained source row. It is not a global employer or vacancy identifier; cross-source reposts remain unresolved.
- `job_skills` is one row per stored record/skill ID. Count distinct `record_id` for a per-skill numerator; do not count raw repeated tokens.
- For a within-skill-data share, divide by distinct records in the same cohort with at least one reviewed eligible skill. For all-record coverage, divide by all retained records in that same cohort. Label the chosen denominator.
- Keep the source and snapshot type with the result. Do not pool different snapshot types into one posting trend.
- Null, blank, unknown, and unverified values remain unknown; do not replace them with zero or infer missing values from another field.

## Implementation boundary

The Node.js API at `backend/node/` reads only the local SQLite database, applies the documented metric/skill policies, and performs deterministic matching in the same process. Python remains the offline loader, analytics, and experiment runtime; it is not invoked by online requests. No hosted database or standalone ML server is used. The full-data API has not yet been reconciled in this checkout because the generated SQLite file is absent.
