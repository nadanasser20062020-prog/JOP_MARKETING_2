# Bug reports — Backend v2

**النطاق:** العيوب التي ظهرت أثناء بناء واختبار `backend_v2` فقط، مع حالة الإصلاح ودليل إعادة الاختبار. الملفات القديمة خارج هذا النطاق ولم تُعدّل.

## عيوب تنفيذية

### BUG-001 — تركيب Markdown غير صالح في تدقيق عائلات الوظائف

- **الأثر:** فشل `npm run check` عند `scripts/audit-job-family-labels.js`، ولم تبدأ الاختبارات في تلك المحاولة.
- **السبب:** صياغة إنشاء Markdown لم تكن سلسلة JavaScript صالحة.
- **الإصلاح:** إعادة تركيب النص إلى أجزاء Markdown واضحة ثم دمجها.
- **الحالة:** **مغلق**.
- **التحقق:** فحص الصياغة النهائي مرّ على 24 ملف JavaScript؛ تقرير التدقيق الفعلي يُكتب بنجاح.

### BUG-002 — بناء فهرسة قاعدة النشر حاول تعديل قاعدة المصدر read-only

- **الأثر:** فشل أول بناء عند `ANALYZE; PRAGMA optimize` برسالة `attempt to write a readonly database` لأن الاستعلام حاول تحديث metadata في قاعدة المصدر المرفقة.
- **الإصلاح:** حصر `ANALYZE` في قاعدة `main` المنشأة.
- **الحالة:** **مغلق**.
- **التحقق:** إعادة بناء كامل من قاعدة NADA المعتمدة نجحت مع `quick_check=ok` ومقارنات صفوف/مهارات/رواتب متطابقة.

### BUG-003 — اعتماد زائد على أعمدة خام اختيارية في `job_skills`

- **الأثر:** fallback الأولي في منشئ قاعدة النشر استخدم `skill_normalized`, `skill_raw`, و`skill_category` رغم أن الواجهة المطلوبة للتطبيق تعتمد `record_id` و`skill_id` فقط.
- **الإصلاح:** ملء المهارات القياسية من جدول `skills`، واستخدام fallback بـ`skill_id` وحده للمعرّفات غير الموجودة بالكتالوج. تمت مراجعة كل استعلامات `analytics-repository.js` و`skill-matching.js` لتتوافق مع `job_skills` view الذي يقدمه ملف النشر.
- **الحالة:** **مغلق**.
- **التحقق:** لا توجد مراجع تنفيذية باقية إلى الأعمدة الخام في استعلامات التطبيق؛ تطابق روابط المهارات `4,026,953`، وجميع 1,498 `skill_id` المصدرية موجودة في الكتالوج؛ نجحت مطابقة المهارات والتحليلات على قاعدة النشر الفعلية.

### BUG-004 — ملف قاعدة النشر الخام تجاوز ميزانية Vercel

- **الأثر:** إسقاط SQLite بحجم `279,310,336` بايت يتجاوز حد دالة Vercel الذي يستهدفه الإعداد.
- **الإصلاح/التخفيف:** بناء gzip مضغوط حجمه `79,477,402` بايت، تضمين gzip في `includeFiles`، وفكّه إلى ملف مؤقت عند التشغيل ثم فتحه read-only. أضيف اختبار وحدة لقاعدة gzip.
- **الحالة:** **مخفف محليًا؛ النشر الفعلي غير متحقق**.
- **التحقق:** اختبار فك الضغط ومخطط read-only، و`db:check` على gzip، وAPI smoke test بوضع `VERCEL=1` كلها نجحت.
- **المتبقي:** توفير ملف gzip في مساحة نشر Vercel، والتحقق من سعة المجلد المؤقت ووقت بدء التشغيل وحجم الحزمة على المنصة الفعلية.

### BUG-005 — إعادة كتابة `/` كانت تشير إلى مسار لوحة ثابت غير منشور

- **الأثر:** `/` كان يعاد توجيهه إلى `/dashboard` رغم أن HTML داخل bundle الدالة وليس ملفًا ثابتًا في جذر النشر.
- **الإصلاح:** إعادة الكتابة إلى `/api/v2/dashboard`؛ أصبح handler يعيد HTML على `/`, `/dashboard`, و`/api/v2/dashboard`.
- **الحالة:** **مغلق**.
- **التحقق:** اختبارات HTTP fixture وطلبات مباشرة على الخادم الفعلي أعادت HTML بحالة `200`.

### BUG-006 — أول تحميل للوحة يحسب تجميعات السوق الثقيلة عند الطلب

- **الأثر:** أول حساب فعلي لـ`GET /api/v2/analytics/dashboard` استغرق نحو **33.3 ثانية** على قاعدة النشر الكاملة. هذه مدة بطيئة وتقلل هامش Vercel.
- **الإصلاح/التخفيف:** إضافة `reports/dashboard-data.json` مُنشأ وقت البناء، مع مطابقة إصدار snapshot على `dataset_metadata.generated_at_utc` قبل استخدامه. عند غياب snapshot أو عدم مطابقته، يعود handler للحساب الحي.
- **الحالة:** **مخفف**.
- **التحقق:** snapshot بحجم 18,284 بايت؛ endpoint أعاد البيانات خلال 4–6 ms محليًا. بعد حذف cache المؤقت المحلي، فك ضغط قاعدة gzip البالغة 79.5 MB وفتحها read-only استغرق 1.092 s، ثم أعاد endpoint snapshot في 6 ms.
- **المتبقي:** وقت cold start الحقيقي على Vercel لم يُقَس؛ قياس 1.092 s من بيئة Node محلية وليس منصة Vercel.

## قيود بيانات يجب عدم تسميتها أخطاء تنفيذ

- من أصل 775,155 سجلًا، `salary_estimation_status` هو `Estimated` في 735,952 سجلًا، `Actual` في 6,937، `Unverified` في 32,206، `Not disclosed` في 56، و`Unparseable` في 4. تبقى قيم التقدير كما هي ومعلّمة بحالتها؛ لا توصف كرواتب فعلية مؤكدة.
- `not_remote_explicit` يغطي 677,472 سجلًا، لكنه لا يثبت حضورًا للمكتب. تعرضه الواجهة بالوصف التحفظي.
- تدقيق المنشأ لا يزال يعرض `NO_GO` لأن `role_family` مشتق ولا يحمل حقول مراجعة بشرية، و`category_raw` متوفر لـ30,333 سجلًا فقط. بحسب طلب المستخدم، لا تعمل هذه الملاحظة كبوابة: دُرّب مصنف مستقل على 775,155 قيمة `role_family`، وأُبلغت نتائج اختبار محجوز (accuracy 94.1457%، macro-F1 76.6955%). هذه مقاييس توافق مع التسميات المشتقة وليست دقة مثبتة على حقيقة أرضية مستقلة؛ التقرير التفصيلي في `reports/job-family-model-evaluation.json`.
- هناك 5,812 موقعًا مصنفًا `unknown` في مقارنة الأسواق؛ لا يُدمج مع العربي أو الدولي.

## مخاطر/قيود مفتوحة

### RISK-001 — تحقق منشأ CSV/SQLite على مستوى السجل

- **الحالة:** **مفتوح كحد تحقق**.
- **المتاح:** تحقق manifest Drive أن `jobs_cleaned_audited.csv.gz` المؤرخ `2026-10-28` يضم 775,155 صفًا؛ كما تطابق في قاعدة NADA أسماء ملفات المصدر السبعة وأعدادها فرديًا مع `cleaning_summary.json` و`source_manifest.csv`.
- **غير المتاح في هذا التنفيذ:** لم تُنزّل أجزاء CSV الثلاثة من مجلد البيانات المنظفة إلى مساحة العمل، لذلك لم يُحسب SHA للنسخة المحلية ولم تُجرَ مقارنة خلية بخلية بين CSV وSQLite. بصمة CSV في Drive ليست بصمة SQLite.
- **القرار:** قاعدة التشغيل ناتجة من أجزاء SQLite الـ11 المعتمدة، لا من نسخة محلية أحدث غير متحققة؛ أسس المطابقة وحدودها موثقة في دفتر الاختبارات.

### RISK-002 — قاعدة النشر المضغوطة متجاهلة بواسطة Git

- **الحالة:** **مفتوح تشغيليًا**.
- **الأثر:** `backend_v2/data/jobs_analytics.sqlite3.gz` مُستثنى وفق `.gitignore` وسياسة إبقاء البيانات خارج Git. لذلك لا يمكن اعتبار Git-based Vercel deployment حاويةً للقاعدة ما لم يُوفّر الملف في خطوة التغليف أو يختَر المستخدم آلية تخزين/تسليم مناسبة.
- **المطلوب قبل النشر:** إعداد artifact provisioning آمن، اختيار `backend_v2/` جذر Vercel، ثم تشغيل build/package/deployment check فعلي على الحساب والمنصة.

### RISK-003 — Vercel لم يُنشر ولم تُبنَ حزمة المنصة

- **الحالة:** **مفتوح حسب النطاق الحالي**.
- **الأثر:** اختبارات الخادم بوضع `VERCEL=1` تختبر اختيار مسار gzip والـhandler محليًا، لكنها لا تثبت runtime/حجم الحزمة/الذاكرة/الوقت على منصة Vercel. لم يتم `vercel deploy`.
